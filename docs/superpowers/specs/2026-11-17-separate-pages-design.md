# Separate the public reader repository

The user approved two repositories: ai-editorial owns collection, selection and standard daily data; ai-editorial-pages owns the reader UI, RSS, archive rendering and website deployment. No third deployment repository. Preserve the existing visual design, automatic operation, free source pack and private workbench.

Use the existing public `https://runchengxie.github.io/ai-editorial/editions.json` as the v1 data contract (a whitelist of at most 30 dated editions). This is already deployed, so the new reader can consume a merged production provider throughout migration. The producer continues to publish JSON on its existing Pages endpoint, while its old HTML entry points become redirects after the new website is live. These redirects are migration infrastructure; no reader templates, CSS, locale UI catalogs or browser tests remain in the engine's daily-data path. The inherited AIHOT dynamic app and internal workbench stay in the engine repository.

The reader performs strict independent validation and whitelisting, rejects malformed URLs/dates, duplicate dates, inconsistent source references, unhealthy source sets, future/stale latest data (48-hour maximum age), and stops before deployment on any failure. It never checks out or imports engine code and never collects news. Its build records source URL, content digest and renderer revision. The provider's canonical v1 schema and consumer validator are tested together with explicit revisions.

Producer schedule remains 08:17 Shanghai daily; reader schedule is 08:37. Both allow manual dispatch. Successful reader main checks also trigger rendering; the producer data workflow runs only on schedule/manual dispatch so migration can merge the provider first without replacing the old site before the reader is deployed. After the new reader is live, manually publish producer data/redirects and render again to verify the full chain. All publication paths require green exact-main checks. No new long-lived GitHub/model credential is required.

Alternatives: cross-repository dispatch needs an additional runtime credential; mutable release assets require extra atomic-pointer machinery; a third repository adds no useful boundary. Chosen: public JSON over HTTPS and independent schedules. Short scheduling delays are acceptable; failed input leaves the last working deployment in place. Generated data remains outside Git. Retain existing history through the unchanged producer state artifact.
